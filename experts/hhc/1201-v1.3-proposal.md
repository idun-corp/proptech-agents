# 1201 Lake Robbins CHW Plant Watch — proposed v1.3 (post chiller-UC onboarding)

Analysis of the onboarded chiller twins against the deployed v1.2 spec
([1201-lake-robbins-chw-plant-watch.md](1201-lake-robbins-chw-plant-watch.md)), plus the
concrete blocks to drop in. Onboarding tracked in **OTEAM-6766** (see also the site
handover). Source of truth for sensors:
`8. Building discovery/HHH/Woodlands/1201/1201_chiller_FDD_catalogue.csv` (440 mapped rows)
and `1201_chiller_keep.csv`.

**Verified final state (2026-08-01):** 5 devices + **490 sensors**
(11001: 119 · 11002: 107 · 11003: 77 · 11004: 81 · 11005: 106). Connector at 129 devices /
8,306 sensors / 22.36 reads/sec (+23% over the 18.12 baseline); 0 timeouts or aborts, 0
chiller-related errors, supervisor 0.733 ms against a 0.84 ms baseline. 439 of 490 sensors
have observations under 5 minutes old; the remaining 51 are 15-min tier mid-cycle.
Mode coverage after the filter fix: refrigerant-leak 58, motor-bearing-thermal 40,
flow-pump-proof 36, oil-system 34.

**The purge signal is live and moving** — 11001 `Daily Pumpout-24 Hours` read 798 at scan
time and 757 shortly after. Note the direction: it is a **rolling 24-hour counter, so it
falls as well as rises** (see Rule 9 — sample at a fixed time of day and never treat a
decrease as a fault).

**Headline:** v1.2's central premise is now obsolete. It says *"this plant has DAILY kWh
registers, not hourly kW"* and *"NEVER copy the 9950 hourly power rules"*. There is now a
**direct `KiloW` point at 1-minute cadence on four of five machines** — so the 9950-style
rules become not just possible but the right design. Three of v1.2's `[CONSTRAINTS]` are
now factually wrong and must change before anything else.

## 1. Data gaps (fix upstream, not in the prompt)

### 1.1 Chiller 11005 has no kW — and no power factor either

11001 and 11002 (same UC800 family) both expose `Starter Input Power Consumption`
(`ActivePowerTotal` / `KiloW`, 1 min). 11005 exposes only `Power Loss Chiller` and
`Momentary Power Loss Chiller` booleans. Confirmed three ways: absent from the keep set,
absent from the dropped set, and absent from the Tracer's own equipment point list for that
machine (which carries `FullLoadKW` nameplate but no instantaneous power point) — so it is
not a scan miss, that machine does not publish it.

**Worse than a missing point: there is no power factor on 11005 either**, so the
`V × I × PF × √3` fallback is unavailable too. Deriving kW there requires an *assumed* PF —
which makes it an estimate, not a measurement. Recommended posture: use **`% RLA`
(`d82c4374-…`) as 11005's load signal**, never publish a derived kW figure for it, and state
the blind spot on every plant-level energy line. Worth a site conversation with
Trane about whether the meter option can be enabled.

**Nameplate trap, second instance:** 11003/11004 expose `Chiller Design Capacity` in
**unit 48 (kW)**. It is nameplate and was correctly dropped, but anything that sniffs
unit 48 looking for live power will grab it. Same class of error as v1.2's
"Full Load KW = 258 is not consumption" — the constraint now needs to name both.

### 1.2 Load signals split by family (counters do NOT — earlier claim retracted)

| Signal | UC800 (11001, 11002, 11005) | CTV (11003, 11004) |
|---|---|---|
| Compressor starts | ✅ `Compressor Starts` | ✅ `Starts - Compressor 1A` |
| Compressor run time | ✅ `Compressor Running Time` | ✅ `Run Time - Compressor 1A` |
| `Actual Running Capacity` | ❌ absent | ✅ |
| Load proxy to use | `Average Motor Current % RLA` | `Actual Running Capacity` (+ RLA) |
| kW point | 11001/11002 ✅, **11005 ❌ (no PF either)** | ✅ `Unit Power Consumption` |

**Retracted:** an earlier draft claimed the CTVs had no starts/run-time counters and that
the purge rule would need a derived-runtime workaround. Both counters exist under different
names and are onboarded, so **short-cycling covers all five machines and purge
normalisation needs no workaround.** The false claim came from reading the catalogue rather
than the raw scan — the same second-hand-evidence trap the naming lesson below warns about.

What *is* family-dependent is the load basis: `% RLA` on the UC800s, `Actual Running
Capacity` on the CTVs. That belongs in the prompt, not discovered at runtime.

### 1.3 Device number ↔ chiller number: CONFLICTING EVIDENCE, unresolved — blocks Rule 8

There are **at least three independent numbering systems** in this plant and they do not
agree. Verified 2026-08-01 against the Tracer evox metadata and the ProptechOS API:

| Source | What it says |
|---|---|
| BACnet device instance | 11001–11005 |
| Tracer equipment instance | `chlr-1`…`chlr-5`, with MS/TP addresses `13.01\|chlr-5` … `13.05\|chlr-1` — i.e. **trunk address counts opposite to the chlr number** |
| Tracer equipment → device link | equipment slot `generic/1` = `netAddr 13.05\|chlr-1` = `deviceUri //bacnet!11005/` → **device 11005 is `chlr-1`** |
| The controllers' own device names (ProptechOS `popularName`) | 11001 `UC800_11001`, 11002 `UC800_11002`, **11003 `Howard Hughes Lake Robbins Chiller 3`**, **11004 `Howard Hughes Lake Robbins Chiller 4`**, 11005 `UC800_11005` |
| Energy registers (meter device `e8cd41ea…`) | `Chiller 1…5 Yesterday kWh` — no physical link exposed |

The conflict: the equipment/trunk evidence implies 11004 = `chlr-2`, but device 11004's own
BAS object name is "…Chiller 4". Only one device↔equipment pair is actually confirmed
(11005 = `chlr-1`); the rest is pattern extrapolation. Note that 11003 = `chlr-3` under
either reading — the midpoint is invariant — so it proves nothing either way.

**Do not guess.** Rule 8 correlates the per-chiller *daily kWh registers* with machine
state; under the wrong mapping every failover conclusion names the wrong machine. Two ways
to settle it:

1. **Cheap:** read the Tracer UI plant graphic — it shows equipment name against the
   physical machine.
2. **Empirical, and the agent can do it:** integrate each device's live 1-min kW over a
   full day and match it against the five `Yesterday kWh` registers. Four of five machines
   have kW, and the daily totals are far apart (1,519 / 6,511 / 4,234 / 0 / 0 in the July
   baseline), so the match will be unambiguous. Run this as a one-off calibration in week 1
   and hard-code the resulting table.

Until it is settled, the agent must report **by device instance only** and never translate
to "Chiller N".

## 2. Constraints in v1.2 that are now wrong

| v1.2 text | Replace with |
|---|---|
| "ALL temperatures in °F … never °C" | Temperatures are stored **per machine**: UC800s (11001/11002/11005) in Fahrenheit, CTVs (11003/11004) in **Celsius**. Convert CTV values `°F = °C × 9/5 + 32` at ingest; *display* everything in °F. A literal threshold like `bearing_temp > 180` is correct for the UC800s and nonsense for the CTVs. |
| "Energy claims only from the daily kWh registers; hourly failure claims only from temps" | Energy and power claims come from the **1-min `KiloW` points** (4/5 machines). The daily kWh registers are demoted to a **cross-check** (see Rule 7'). |
| "NEVER copy the 9950 hourly power rules — this plant has DAILY kWh registers, not hourly kW" | Delete. The 9950 power rules are now the *preferred* design here, with 1-min data that 9950 didn't have until 08/01. |

Also **extend** the nameplate constraint. v1.2 says "Full Load KW = 258 is nameplate, not
consumption"; it must now also name `Chiller Design Capacity` on 11003/11004 (unit 48, kW).
State the rule as intent, not as a list: *nameplate/design/limit registers are never
consumption, regardless of their unit* — a kW unit is not evidence of a live power reading.

Keep unchanged: no actuation, MM/DD/YYYY + 12-h CT, the benign 4–7 AM morning-blip
exception, data gaps → DATA ISSUE, tilde ban, both-supply-sensors-agree before a 🔴 outage
call.

## 3. Structural recommendation: split into two agents

490 sensors cannot be read in one tick. The 9950 PdM agent's 08/01 failure is the precedent
— truncated UUIDs forced `search`/`fetch` name resolution and it timed out 13 times. Apply
the same fixes that rescued it:

- **Ops agent (hourly)** — thin, fast, current-fault detection. Fetch budget ~20 calls:
  5 × kW/RLA to find who's running, then 6–7 points per running machine (typically 2–3
  running).
- **PdM agent (daily, 3:00 PM CT)** — trend work: purge, oil, bearing/winding, starts,
  approach, efficiency drift. Cumulative CSV ledger carried forward in its own report,
  same mechanism as 9950.

Both get: **full UUIDs in the prompt** (never name resolution — the two families use
different names for the same signal, so name matching is actively unsafe), a **hard tool
whitelist** (`get-sensor-latest-data`, `get-sensor-historical-data` only), a fetch budget,
and degraded mode after two consecutive timeouts.

Cadence bounds the windows: counters are on the **15-min tier**, so no rule may claim
resolution finer than 15 minutes (e.g. "starts per hour" is the floor, not "per minute").

## 4. Rules to add / revise

### Rule 0 — RUN GATE (new; not a fault, the precondition for everything quantitative)

```
running(machine) = Chiller Running/Running State == true  AND  %RLA > 15
```

Idle machines read **zero, not null** — zero amps, zero kW, IGV 0. Every quantitative rule
below must be gated on this, or an idle machine looks like a catastrophic failure. Also
keep v1.2's warning that an idle chiller's water temps read stagnant barrel water.

### Rule 1' — POWER WITHOUT COOLING → 🔴 CRITICAL (new; the 9950 signature, now possible)

```
running AND kW > 20 AND evap_leaving > 44 °F AND dT < 5 °F  for ≥ 2 consecutive hours
```

Per machine, using that machine's own evap entering/leaving pair (both exist on all five).
This is the failure that cost 9950 approx. 1,500 kWh per event, twice in July, and until
today it was undetectable at 1201.

### Rule 2' — CAPACITY STRAIN → 🟡 WARNING

```
running AND evap_leaving > 44 °F AND dT ≥ 10 °F  for ≥ 2 consecutive hours
```

Distinguish from Rule 1' by dT: low dT = broken, high dT = overloaded. At 9950 this was the
4-day precursor to the 07/10 failure.

### Rule 4' — FLOW LOST WITH COMPRESSOR RUNNING → 🔴 CRITICAL (new, highest urgency)

```
running AND (Evaporator Water Flow Lost/Status == lost OR Condenser Water Flow Lost == lost)
```

Freeze risk on the evaporator, high-head trip on the condenser. Alert on the **first
sample** — no 2-hour persistence — this is a protect-the-asset condition. These are the 32
points the option-A filter had dropped; note the naming split (UC800 `Evaporator Water Flow
Lost Chiller` vs CTV `Evaporator Water Flow Status`), another reason to bind by UUID.
Also watch the `… Overdue` variants as a 🟡 precursor (pump commanded, proof not yet made).

### Rule 9 — PURGE / AIR INGRESS TREND → 🟡 P3 rising to P2 (new; the headline)

```
daily_pumpout_24h, sampled at a FIXED time of day, rising week-over-week
  per run hour  → P3 watch; sustained 3+ weeks or >2× baseline → P2
```

R-123 machines run below atmospheric, so a breach draws **air in** rather than leaking
refrigerant out — pumpout rate is the leading indicator, weeks to months of lead time.

**It is a rolling 24-hour counter, not a monotonic total.** Observed on 11001: 798, then
757 a short while later. So:

- **Never treat a decrease as a fault** — and never compute a "delta since last tick" the
  way the 9950 spec does for `Compressor Starts` (that one *is* monotonic). Different maths.
- **Sample at a fixed time of day** and compare like-for-like across days. The daily
  3:00 PM CT PdM tick does this naturally; an hourly agent must not trend this point.
- Trend the **7-day mean**, not consecutive readings — the rolling window already smooths
  within a day, and the 15-min tier bounds resolution.

Normalise by run hours — available on **all five** machines (`Compressor Running Time` on
UC800s, `Run Time - Compressor 1A` on CTVs) — so a busier machine doesn't look like a leak.
Cross-read `Pumpout Chiller On/Off-7 Days` (%) and `Time Until Next Purge Run`;
`Pumpout-Life` is the odometer, context only. This mode was unobservable at every HHH site
before today — it is the reason this onboarding was worth doing.

### Rule 10 — SURGE / IGV → 🟡 (new)

`Differential Refrigerant Pressure` (KiloPA) rising while `IGV1 Position` opens and `%RLA`
stays flat, or any `Extended Compressor Surge` alarm true. Surge is the centrifugal killer.

### Rule 11 — OIL SYSTEM → 🟡 P2 (new)

Two layers now that `AlarmMinor` points are onboarded:

- **Trend:** `Oil Differential Pressure` 7-day slope negative **and** >15% below its 30-day
  mean at comparable load. All five machines have oil ΔP.
- **Trip:** the `Low Differential Oil Pressure` alarm bit → immediate 🟡, and 🔴 if it
  coincides with the machine running. This is a protection trip, not a trend — do not wait
  for a slope.

### Rule 12 — MOTOR / BEARING THERMAL → 🟡 (new)

Bearing (inboard/outboard) and the three winding temps trending up at comparable load,
**plus** the bearing/winding high-temperature alarm bits (now onboarded) as the trip layer.
Use **unit-aware thresholds** — this is the rule most likely to be silently broken by the
F/C split, and the one where a literal `> 180` would read as normal on a Celsius machine.

### Rule 13 — APPROACH, COMPUTED (new; do not use the stored points)

The stored approach temperatures are delta-degrees in a Trane proprietary unit, typed
`Index` rather than a temperature, and unreliable while the machine is off. **Compute
approach yourself** from water temps and saturated-refrigerant temps, then trend it:
condenser approach rising at constant load → fouling or air ingress (corroborates Rule 9);
evaporator approach rising → fouling or low charge.

### Rule 7' — ENERGY, now live + the registers as a cross-check (replaces v1.2 Rule 7)

Report live plant kW each tick (sum of the 4 available machines, blind spot on 11005
stated). Keep the daily `Yesterday kWh` band check at the 7:00 AM tick, but its new job is
**validation**: integrate the 1-min kW over the day and compare to the register. A
persistent divergence is a meter/register problem → 🟡 DATA ISSUE. Per-chiller registers
must still sum to the Total.

### Rule 8' — FLEET MIX SHIFT (revised)

Same intent, now with same-hour latency instead of one day — a failover shows up as one
machine's kW collapsing while another's jumps. **Uses the verified device↔chlr mapping from
§1.3**; until that's confirmed, report by *device instance* only and do not translate to
"Chiller N".

### Rule 14 — EFFICIENCY kW/ton (new, conditional)

There is **no flow measurement on the chiller UCs**. kW/ton needs evaporator flow from
plant device 11015 (`0986975a-…`), or use `%RLA` / `Actual Running Capacity` as a load proxy
and track *relative* drift only. State which basis was used in every efficiency claim.
Only 11001 has an AFD (`AFD Output Power`, 19 drive-health sensors) — drive rules apply to
that machine alone. **Exclude 11005 from any kW-based efficiency claim** — no kW and no PF
means no defensible power figure (§1.1); track it on `% RLA` drift alone and say so.

### The naming lesson (durable, carried in the handover)

Both onboarding misses came from **filtering keep-rules by name**: first `CapabilityTypeState`
gated on `status|mode|running`, which the CTVs' "…Water Flow Status" satisfied and the
UC800s' bare "Evaporator Water Flow" did not; then `AlarmMajor` only, which dropped every
`AlarmMinor` trip including `Low Differential Oil Pressure` and the bearing/winding
high-temp bits. Replaced with a semantic test over trip/protect meaning across **both**
alarm classes.

The durable rule: **stop filtering by name; don't rename to make filters work.** With two
families wording the same signal differently, any name list is incomplete by construction.
Renaming to force uniformity would also destroy traceability back to the BAS and to the
scan. Select on *meaning* (quantity kind, alarm class, protect/trip semantics), bind on
*UUID*, and keep the vendor's own wording in `popularName`.

The same trap applies to the agent: it must never resolve a sensor by name, because the
two families disagree on wording for identical signals — and it applies to reviews too, as
the retracted §1.2 counter claim shows (read the scan, not a derived catalogue).
